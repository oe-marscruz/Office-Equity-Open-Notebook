They assume shared controls and one maintained backend, reuse of upstream features, and applicability decisions instead of automatically building a new SIS or institutional records platform.

Next priorities are F05's assembled backend and F04's credential migration/provisioning, then packaged-application acceptance for F03. F07/F08 and F17 can progress alongside the three-configuration architecture work in F11. Existing FERPA documents remain requirement inputs; these estimates are not acceptance evidence.

## Verification and bridge handoff

Use the mandatory commands from the repository root:

```text
npm run build:types
node scripts/orchestrator/verifier.js
```

The initial build failed because its cleanup used Unix `rm`. The build script now uses Node's cross-platform filesystem API. The refreshed lockfile matches the declared build dependencies, and installation used `npm ci --ignore-scripts --no-audit --no-fund`.

The initial verifier passed 25 of 27 checks. Its two existing failures were an absent performance baseline and an unreliable literal-port-zero HTTP test. The performance baseline was added upstream in `fbc0ff3`; the readiness test is repaired on this branch, because port `0` resolves to a real listener on Windows and returns a status instead of failing as the test assumed.

Observed results on the ported branch:

```text
npm run build:types                                   PASS
node scripts/orchestrator/verifier.js                PASS (28/28 suites)
node scripts/tests/test-service-diagnostics.js        PASS
cargo check --offline --manifest-path src-tauri/Cargo.toml   PASS
cargo test --offline --manifest-path src-tauri/Cargo.toml --test service_diagnostics   PASS (3/3)
```

The native check needs the pinned upstream checkout present at `../open-notebook` relative to `src-tauri/`, because `tauri.conf.json` points `bundle.icon` at an upstream asset. CI provides that checkout; a local run without it fails in `tauri-build`, not in this change.

The L8.2 regression test first reproduced the unsupported legacy report, then passed after implementation. A second negative test reproduced acceptance of malformed nested evidence; the validator was tightened to reject it. The generated L8.2 JSON report is intentionally retained as fixture evidence. Other generated test artifacts should not be included as new security assurance.

## References and decisions still needed

Local sources: `FERPA_Software_Testing_Compliance_Checklist.docx` (all five domain tables); `FERPA_Compliance_Software_Practical_Guide.docx` (sections 2 to 4); `Microsoft_Azure_FERPA_Implementation_Guide.docx` (sections 4 to 6); `Microsoft_Azure_FERPA_Compliance_Framework_Mapping.docx` (control mapping table). These guides are supplied reference inputs, not proof of implementation or institutional approval.

The checklist's 15-minute timeout, AES-256, WORM logging, alert timings and example retention periods are project criteria to confirm with policy owners, not universal technical requirements imposed by FERPA. Apply the governing [Department of Education regulations](https://studentprivacy.ed.gov/ferpa), including recordkeeping exceptions, to the actual use case.

Cloud evidence must follow the selected deployment model and [Azure shared responsibility](https://learn.microsoft.com/en-us/azure/security/fundamentals/shared-responsibility). For concrete cloud preparation, use [Key Vault security guidance](https://learn.microsoft.com/en-us/azure/key-vault/general/secure-key-vault) and [Azure Monitor diagnostic settings](https://learn.microsoft.com/en-us/azure/azure-monitor/data-collection/diagnostic-settings). Resource logs need configured destinations; a Log Analytics workspace alone does not establish immutable storage.
